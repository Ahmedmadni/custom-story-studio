# Architecture

Phase 10 of the Production Hardening & Launch Preparation Sprint — a
system-level map of Kidzy (حكايتي) as it exists in this repo today,
written for a developer joining the project cold. For deeper detail on
any one area, see the phase-specific docs this sprint produced:
`docs/SECURITY-AUDIT.md`, `docs/EMAIL-ARCHITECTURE.md`,
`docs/ERROR-HANDLING.md`, `docs/PERFORMANCE-AUDIT.md`,
`docs/DATABASE-AUDIT.md`, `docs/BACKUP-PLAN.md`, `docs/OBSERVABILITY.md`,
`docs/LAUNCH-CHECKLIST.md`.

## System overview

Kidzy is an AI-personalized children's story platform for the
Egyptian/Arabic market. A parent uploads a photo and details of their
child; the app generates an illustrated, personalized story or
educational book, an admin reviews and approves it, and it's delivered as
a print-ready PDF (and shareable via WhatsApp).

```
Parent (browser, RTL Arabic UI)
   │
   ▼
TanStack Start app (React 19, SSR + client) ── deployed to Cloudflare Workers via nitro
   │                                    │
   ├── Supabase (Postgres + Auth + Storage) ── source of truth for everything
   │                                    │
   ├── Lovable AI functions ── story text + image generation
   │                                    │
   └── Kashier ── card payments (webhook-driven)
```

## Frontend

### Framework & routing

- **React 19** on **TanStack Start** (Vite 7), file-based routing under
  `src/routes/`. Route files are named by URL segment with `.` as the
  separator (e.g. `_authenticated.admin.orders.tsx` →
  `/admin/orders` inside the authenticated layout); a literal dot in a
  path (like `/sitemap.xml`) is escaped as `[.]` in the filename
  (`sitemap[.]xml.tsx`).
- `_authenticated.tsx` is a pathless layout route — every route nested
  under it (`_authenticated.*`) requires a logged-in Supabase session.
  `_authenticated.admin.tsx` nests one level further and additionally
  requires the `admin` role (checked via the `has_role` RPC).
- `src/routeTree.gen.ts` is generated by `@tanstack/router-plugin` at
  build time — never hand-edited (enforced by `CLAUDE.md` convention,
  though this sprint's Phase 5/6 work confirmed by direct inspection that
  route-based code splitting is real: every route file produces its own
  JS chunk).
- `src/router.tsx` creates the `QueryClient` (React Query) and the
  TanStack Router instance; `defaultPreload: "intent"` prefetches route
  data on link hover/touch, and (as of this sprint's Phase 5) the
  `QueryClient` has a `staleTime`/`gcTime` default to reduce redundant
  refetching.

### Styling

Tailwind CSS v4 + shadcn/ui (Radix UI primitives under `src/components/ui/`).
RTL-first (`dir="rtl"` on `<html>` in `src/routes/__root.tsx`), Arabic UI
throughout. Design tokens live in `src/styles.css` — a purple `#6C4DFF`
primary, large rounded cards, soft shadows, mobile-first.

### State management

- **Server state**: TanStack Query (`@tanstack/react-query`) for all
  data fetched from `createServerFn` server functions — no separate
  client-side data-fetching library.
- **Client/UI state**: React hooks + a small number of context providers
  wired in `__root.tsx`'s `RootComponent`: `AuthProvider` (session/user),
  `CartProvider` (shopping cart), plus always-mounted app-shell widgets
  (`OfflineBanner`, `ReferralCapture`, `OnboardingWizard`) and, as of this
  sprint's Phase 4, an `ErrorBoundary` wrapping `<Outlet />` as a
  render-error safety net alongside the router's own `errorComponent`.
- **Forms**: `react-hook-form` + `@hookform/resolvers` (Zod schemas).

### Component organization

- `src/components/` — shared, cross-feature UI (design system primitives
  under `ui/`, plus app-level widgets like `Header`, `Footer`,
  `TrustCounters`, `PortfolioGallery`, `ErrorBlock`, `ErrorBoundary`).
- `src/features/<domain>/` — business-logic-adjacent components co-located
  with their domain (e.g. `features/pdf/PdfActions.tsx`,
  `features/library/StoryCard.tsx`, `features/admin/OrdersManager.tsx`).
- `src/routes/*.tsx` — page-level components, generally thin: fetch data
  via server functions, compose feature components.

## Backend

### Supabase (Postgres + Auth + Storage)

- **Schema**: plain numbered SQL files in `supabase/migrations/*.sql` (36
  as of this sprint — no Prisma/Drizzle). **Important caveat, verified
  repeatedly across this sprint's audits**: `profiles`, `orders`,
  `user_roles`, `story_templates`, and `generated_pages` were created
  before migration tracking began — their base schema exists only in the
  live database, not in this repo (see `docs/SECURITY-AUDIT.md` §1,
  `docs/DATABASE-AUDIT.md` intro, `docs/BACKUP-PLAN.md` §1.2).
- **RLS**: every table has row-level security enabled with explicit
  policies — an owner-scoped policy (`auth.uid() = user_id` or an
  `EXISTS` join through an owned parent row) plus an admin-override
  policy (`has_role(auth.uid(), 'admin')`), following the same shape
  throughout the schema.
- **RPCs**: `has_role` (the RLS helper itself, called pervasively),
  `award_points`, `calc_child_level`, `complete_story_for_child` — the
  latter three are `SECURITY DEFINER` and `REVOKE`d from
  `PUBLIC/anon/authenticated`, callable only via the service-role client
  or (for `complete_story_for_child`) a trigger.
- **Triggers**: `update_updated_at()` (generic, on most tables with an
  `updated_at` column), `grant_welcome_bonus()` (on `auth.users` insert),
  `trg_orders_on_sent()` → `complete_story_for_child()` (on `orders.status`
  transitioning to `sent`), `set_referral_code()` (on `profiles` insert).
- **Storage buckets**: `child-photos`, `payment-receipts`,
  `reference-children`, `story-pages`, `story-pdfs` — all owner-scoped via
  RLS-equivalent storage policies (path-prefix or order-ownership checks),
  with admin override.
- **Auth**: Supabase Auth (`auth.users`), roles tracked separately in
  `public.user_roles` (not a column on `profiles`), checked via
  `has_role()` rather than trusting client-supplied role claims.

### Server functions

Business logic lives in `src/features/<domain>/*.functions.ts`, each
exporting `createServerFn()`-wrapped handlers (TanStack Start's RPC-style
server functions — called from the client like normal async functions,
executed server-side). Domains: `admin`, `ai`, `cart` (client-only, no
server functions), `children`, `games`, `library`, `notifications`,
`onboarding`, `orders`, `payments`, `pdf`, `puzzles`, `referrals`,
`reviews`, `rewards`, `stats`.

Server-only code (anything touching `SUPABASE_SERVICE_ROLE_KEY` or other
secrets) lives in files ending `.server.ts` — a Vite-enforced convention
that excludes them from the client bundle. The service-role client
(`src/integrations/supabase/client.server.ts`, bypasses RLS) is always
**dynamically** imported (`await import(...)`) inside a handler body, never
imported statically at module top-level — verified across every
`*.functions.ts` file in this sprint's Phase 1 security audit.

### External integrations

- **Lovable AI functions** (`src/integrations/lovable/`) — story text and
  image generation (both cartoon and photo-realistic-in-scene art modes).
- **Kashier** (`src/features/orders/kashier.functions.ts`,
  `src/routes/api/public/kashier.webhook.ts`) — card payment provider;
  order verification is webhook-driven, every event logged to
  `payment_logs` regardless of outcome.
- **WhatsApp** (`src/features/orders/whatsapp.ts`) — deep-link (`wa.me`)
  based sharing/notification, not an API integration (no WhatsApp
  Business API credentials involved).
- **Email** (`src/features/notifications/`) — provider-abstracted this
  sprint (Phase 3): `EmailProvider` interface with `MockProvider` (active
  by default), `ResendProvider`, and a stubbed `SMTPProvider`. **Not yet
  sending real emails** — infrastructure only, see
  `docs/EMAIL-ARCHITECTURE.md`.

### Deploy target

Cloudflare Workers, via `nitro` (configured through
`@lovable.dev/vite-tanstack-config`, which wraps `tanstackStart`,
`viteReact`, `tailwindcss`, `tsConfigPaths`, and Cloudflare-specific
build/deploy plugins). No `wrangler.toml` is checked into this repo — it's
generated at build time. Environment variables/secrets are bound
per-request by Cloudflare Workers (not read at module scope — see
`src/lib/config.server.ts`'s pattern, required because Workers don't have
a persistent process-level `process.env` the way Node does).

## Business systems

- **Child Profiles** (`child_profiles`) — a parent's children, each with
  name, age, photo, personality traits, etc. Owner-scoped, cascades from
  `auth.users`.
- **Story Universe / Story Hero system** (`child_story_universe`,
  `child_story_history`) — per-child leveling (10 XP tiers via
  `calc_child_level`), achievements (`jsonb` array of unlocked achievement
  keys), story-completion history. Driven entirely by
  `complete_story_for_child()`, triggered automatically when an order's
  status reaches `sent`.
- **Rewards / points** (`reward_accounts`, `reward_transactions`,
  `award_points` RPC) — a ledger-style points system: signup welcome
  bonus, referral reward, story-completion reward, review reward all flow
  through the same `award_points()` function, giving a single consistent
  audit trail of every point grant. **Not yet verified wired into
  checkout** as a redemption/discount mechanism (flagged in
  `docs/LAUNCH-CHECKLIST.md`).
- **Achievements** — encoded as a `jsonb` array on
  `child_story_universe.achievements`, computed inline inside
  `complete_story_for_child()` from category-matching queries against a
  child's story history (not a separate achievements table).
- **Referrals** (`referrals`, `profiles.referral_code`) — every user gets
  a shareable code (auto-generated on profile creation via
  `set_referral_code()` trigger). Hardened this sprint (Phase 2): a
  referral starts `pending` at signup (invited user still gets an
  immediate 10% welcome coupon — self-limiting, no cash value) and the
  inviter's 100-point reward is only issued after the invited user's
  _first verified order_, closing a fake-signup-farming hole in the
  original "signup → reward" design.
- **Coupons** (`coupons`, `coupon_redemptions`) — percent/fixed discounts,
  category scoping, min-order thresholds, global and per-user usage caps.
  The `coupons` table's read policy was tightened this sprint (Phase 1) to
  stop non-admin users from enumerating all active codes.
- **Reviews** (`reviews`) — admin-moderated (`is_published` gate) parent
  reviews of completed stories, reward-on-submission, powers both a
  dedicated reviews section and the portfolio gallery's star ratings.
- **Analytics** (`src/features/admin/analytics.functions.ts`,
  `/admin/analytics`) — an admin-facing dashboard built directly on
  `orders`/`payment_logs` aggregate queries (no separate analytics/events
  pipeline or third-party analytics SDK).

## Deferred / partial systems

Per this sprint's explicit "no major new features" scope, the following
are either intentionally stubbed, partially wired, or acknowledged as not
yet built — listed here so their state is explicit rather than implied:

- **Kashier**: fully wired for the happy path (webhook → `payment_logs` →
  order status update → referral reward trigger), but its available
  _dashboard tier/rate limits and dispute-handling process_ are outside
  this repo's visibility — an operational, not code, gap.
- **Printing**: the app produces print-ready PDFs
  (`src/features/pdf/storyPdf.ts`, `jspdf` + `html2canvas-pro`) and an
  order can be flagged `print_copy` with a `delivery_address`, but there
  is **no integration with an actual print/fulfillment vendor** in this
  codebase — the PDF is generated and delivered digitally; physical
  print fulfillment (if `print_copy` orders exist) appears to be a manual
  admin/business process today, not automated.
- **Audio Stories**: no text-to-speech, audio file storage, or audio
  playback UI exists anywhere in this codebase. Not started.
- **Mobile App**: this is a responsive web app (mobile-first Tailwind
  layout, RTL, touch-friendly), not a native or wrapped mobile app — no
  React Native/Capacitor/Cordova scaffold, no app-store presence. Not
  started.
- **Email sending** (Phase 3 this sprint): the provider abstraction exists
  and is fully built, but `EMAIL_PROVIDER` defaults to `mock` — no real
  email is sent to users yet. Activating it is a config change
  (`EMAIL_PROVIDER=resend` + `RESEND_API_KEY`) plus wiring `sendXEmail()`
  calls into the actual event flows (order received, payment confirmed,
  etc.) — infrastructure only, deliberately not activated this sprint.
